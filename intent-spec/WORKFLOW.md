# Personal Agent 协作规范

本文档定义本仓库从「需求确认」到「合并关闭」的完整协作流程，供人类协作者与 AI 协作者共同遵循。

适用范围：`NaoYUN77/personal-agent`。若本文档与某次 Issue 中用户明确给出的指示冲突，以该次指示为准，并在事后修订本文档。

---

## 1. 角色与职责

| 角色 | 职责 |
|---|---|
| 用户 | 决定目标、范围和取舍；确认 spec；决定是否合并 |
| Codex | 澄清需求；编写 Issue；审阅实现与验收证据 |
| WorkBuddy | 认领可执行 Issue；实现、验证并提交 PR |

**实现依据**是 Issue 中已确认的 spec 和验收标准，不是对话过程中的口头补充。

- 遇到影响对外行为的歧义：在 Issue 中提出问题，不自行决定。
- **不得自行扩大范围**，也不得用自己的解释替代验收标准。
- 常规内部实现选择（命名、文件组织、局部重构）可以自行决定。

---

## 2. 生命周期

```text
spec 确认
  → status:ready
  → 认领
  → 实现和验证
  → 提交 PR
  → Codex 审阅
  → 修正并复验
  → 用户决定合并
  → Issue 关闭
```

这是一条不可跳步的链路。**提交 PR 不等于任务完成**，只有验收通过并合并后才关闭 Issue。

## 3. Label 规范

### 3.1 两类标签，两种含义

| 类别 | 回答的问题 | 不表示什么 |
|---|---|---|
| `type:*` | 这个任务**是什么类型** | 不表示已完成 |
| `status:*` | 这个任务**当前是否具备执行条件** | 不表示已完成，也不代替 assignee、PR 或测试结果 |

正常情况下一个 Issue 带**一个** `type` 标签和一个 `status` 标签。范围包含多个独立目标时，优先拆分 Issue。

### 3.2 类型标签

| Label | 含义与动作 |
|---|---|
| `type:bug` | 行为违反已有 spec；需说明复现步骤、期望行为与实际行为 |
| `type:documentation` | 文档或协作流程变更 |
| `type:feature` | 新增能力；需明确输入、输出与行为合同 |
| `type:refactor` | 保持外部行为的内部调整；需说明"行为保持不变"的证据 |

### 3.3 状态标签

| Label | 含义 | WorkBuddy 应如何处理 |
|---|---|---|
| `status:needs-clarification` | 关键需求或验收标准尚未明确 | 可以调查、提出具体问题；**不开始依赖该答案的实现** |
| `status:ready` | spec 已获用户认可，实施已授权 | 可以认领、建分支、实现并提交 PR |
| `status:blocked` | 存在明确阻塞，当前无法继续 | 在评论中写明阻塞原因、影响范围和解除条件 |

### 3.4 使用规则

1. 每个开放的 Issue 原则上只保留**一个**状态标签。
2. **只有用户认可 spec 后，才能设为 `status:ready`。** 用户说"按这个方案提 Issue"也视为认可。
3. **WorkBuddy 不得自行把尚未澄清的需求改为 `ready`。**
4. `ready` 不是"无人认领"的意思。认领之后仍保留 `ready`，由 assignee 表示执行者。
5. 工作中遇到阻塞，可以改为 `blocked`，但**必须留下说明**。
6. 原 spec 未变且阻塞已解除，可以恢复 `ready`；若解决方案改变了 spec，需要重新确认。
7. **有 PR 不代表完成。** Issue 在验收通过并合并后关闭。

## 4. 认领规范

### 4.1 认领前的检查

开始前必须逐项确认：

- [ ] 已阅读**完整** Issue、相关评论和适用的 `AGENTS.md`
- [ ] 标签为 `status:ready`
- [ ] 没有已有 assignee、认领评论或关联 PR（避免重复实施）
- [ ] 记录了当前基准 commit
- [ ] 准备使用独立分支，不直接在 `main` 上实施

### 4.2 认领评论格式

```markdown
已认领本 Issue。

- 认领人：<执行者>
- 基准 commit：`<SHA>`
- 实施分支：`<branch>`
- 预计修改范围：<目录或模块>
- 验证方式：<对应各条 AC 的测试和命令>
- 已知疑问或阻塞：无 / <具体说明>
```

**能设置 assignee 时同步设置**；无法设置时，认领评论本身即为有效认领。

### 4.3 认领之后

认领后如发现需求缺口：

- 明确指出**受影响的 AC**；
- 停止依赖该答案的部分；
- 其他独立工作可以继续。

## 5. 分支与 commit

### 5.1 分支

```text
workbuddy/issue-<编号>-<简短描述>
```

从认领时的 `main` 建立。**不直接推 `main`。**

### 5.2 Commit

格式：

```text
<type>(<scope>): <具体变化>
```

`type` 取值：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`

示例：

```text
feat(notion): read paginated page blocks
fix(cli): return nonzero exit code for unanswered submissions
test(durable): verify submission recovery across process restart
docs(workflow): define issue and PR handoff rules
```

要求：

- 一次 commit 围绕**一个**清晰目的。
- 描述**具体变化**，避免 `update`、`done`、`fix all` 这类空泛措辞。
- 测试与实现可以放在同一 commit。
- 不混入无关的格式化、文件删除或依赖升级。
- 依赖变化必须包含对应 lockfile，并说明原因。
- **不提交**密钥、运行数据库、日志、`node_modules` 或临时产物。
- staging 使用**明确文件路径**，提交前检查 diff。
- Git push 使用已配置的 SSH；Issue、PR 和评论通过 GitHub UI、API 或可用 CLI 操作。

## 6. Issue 模板

新的 Issue 应包含以下结构。**区分"已验证事实 / 推断 / 未知"**，不要把推断写成事实。

```markdown
## 目标与用户场景
<要解决什么问题，谁在什么场景下受益>

## 现状与差距
- 已验证事实：<附文件、行号或命令输出>
- 推断：<说明推断依据>
- 未知：<尚不确定的部分>

## 范围与非目标
- 范围内：<...>
- 非目标：<明确排除的部分>

## 行为合同
<输入 → 输出 / 状态变化；边界条件与错误处理>

## API / 依赖与源码依据
<引用的 API 基于锁定版本的源码，不凭印象编造>

## 验收项
- AC-01：<可判定真假的陈述>
- AC-02：<...>

## 验证前提 / 命令 / 预期结果
<前置条件；命令；预期输出或退出码>

## 允许修改范围
<哪些文件或目录可以动，哪些不能>

## PR 交付要求
<PR 必须包含的栏目与证据>
```

**纯文档任务无需添加虚假的运行 API 描述或 smoke test 要求。**

## 7. PR 规范

### 7.1 标题

写清**最终行为**，并关联 Issue：

```text
docs(workflow): define issue and PR handoff rules (#1)
feat(notion): support paginated page content reads (#12)
```

不要只写"完成 TASK-002"这类无信息量的标题。

### 7.2 正文栏目

正文必须包含以下八个栏目。模板见 `.github/pull_request_template.md`。

1. **关联 Issue** —— `Closes #<编号>`
2. **问题与结果** —— 改动前存在什么问题；改动后用户会观察到什么行为
3. **修改范围** —— 文件/模块、接口或配置变化、依赖变化
4. **验收对应** —— 表格：验收项 ｜ 实现位置 ｜ 验证方式 ｜ 结果
5. **实际验证** —— 环境、被验证的 commit SHA、实际执行的命令、结果及其证明的行为
6. **未执行的验证** —— 命令、原因、受影响的 AC；没有则写"无"
7. **风险与限制** —— 实际存在的限制；没有则写"无"
8. **与 spec 的差异** —— 无，或差异及用户确认该变更的链接

**正文必须描述 PR 的最终实现**，不要用聊天过程或尝试记录替代变更说明。

### 7.3 Draft PR

以下情况**使用 Draft PR**：

- 必需 AC 尚未实现；
- 必需验证尚未完成；
- 存在待确认的 spec 变更；
- 存在阻塞或已知失败。

### 7.4 请求审阅的前置条件

- 所有必需 AC 已实现；
- 必需检查**已实际执行**；
- PR 正文与最新代码一致；
- diff 中没有无关改动；
- 未解决的限制已明确列出。

如果某项必需验证因环境限制无法执行，**保持 Draft**，或在 Issue 中取得对验收安排的明确确认。

## 8. 审阅与回应

### 8.1 回应格式

审阅意见应逐条回应：

```markdown
已修复：<问题>
- commit：<SHA>
- 实现位置：<路径/函数>
- 验证：<命令及实际结果>
```

**如不认同，说明源码依据和复现结果**，不要只写"已处理"。

### 8.2 处理方式

| 情况 | 处理 |
|---|---|
| 当前 spec 未满足 | 在当前 PR 修复 |
| 发现独立缺陷 | 建立关联 Issue |
| 需要新增能力或扩大范围 | 由用户与 Codex 澄清后形成新 Issue |
| spec 本身有歧义 | 先澄清；**不能通过实现悄悄改变约定** |

更新代码后，**重新运行受影响的验证**并同步 PR 正文。
**不得把旧 commit 的结果当成新 commit 已验证。**

---

## 9. 合并与关闭

- **WorkBuddy 不自行合并 PR，也不在实现结束时提前关闭 Issue**，除非用户明确授权。
- 合并由用户决定。
- Issue 在验收通过并合并后关闭。

---

## 10. 验证证据要求

以下证据**不能互相替代**：

| 证据 | 能证明什么 |
|---|---|
| 类型检查通过 | 类型和接口使用符合检查范围 |
| mock / faux 测试通过 | 指定模拟场景下行为正确 |
| 真实 API smoke test | 指定环境下真实服务链路可用 |
| 重启读取成功 | 已提交数据能重新打开 |
| 强制中断后恢复成功 | 被中断任务在重新启动后得到处理 |

特别要求：

- **不把 faux provider 成功写成真实 DeepSeek 成功。**
- **不把"任务完成后 reopen"写成"执行中崩溃恢复"** —— 两者是不同的能力。
- 不把"打印了恢复结果"作为同一 Task 恢复的唯一证据，应记录 ID 和中断前后的状态。
- **不把 `status=unanswered`、HTTP 错误或空答案写成成功。**
- **不仅引用 README 中的历史结果**，应报告当前 PR 实际执行的验证。
- 未配置凭据的真实 API 测试**明确写"未执行"**，不得推断通过。
- 日志只提供必要摘要，**不包含凭据或无关页面内容**。

需要真实凭据、特定 workspace 或外部资源的验证，必须注明前置条件。

---

## 11. 凭据与权限

- 代码推送使用 **SSH key**（`git@github.com`）。
- Issue / PR / 评论使用 **Personal Access Token**（HTTPS API）或已认证的 GitHub CLI。
  - SSH key **无法**执行 Issue、PR 和评论操作——它们不是 git 对象。
- Token 存放于仓库之外的受保护路径，**权限设为仅本用户可读**。
- Token **不得**出现在源码、commit、日志、Issue 或 PR 正文中。
- 一旦凭据以明文形式泄露到任何持久位置，应**立即 revoke 并重建**。
